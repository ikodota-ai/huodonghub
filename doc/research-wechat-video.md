# 微信视频提取可行性实测（2026-09-16）

## 测试对象

用户提供的视频号分享链接：`https://weixin.qq.com/sph/AUbUL8HWy`（账号"就是乐生活"的视频）。

## 实测过程与发现

1. **链接跳转**：sph 链接 301 到 `https://channels.weixin.qq.com/finder-preview/pages/sph?id=AUbUL8HWy`，这是官方网页预览页，桌面浏览器可打开。
2. **页面内容**：预览页只展示元信息——标题、封面图、账号名、日期、互动数，并提示"可扫码前往微信观看此内容"。**页面里没有 `<video>` 元素，没有任何视频文件地址**（已检查 DOM）。
3. **数据接口**：页面通过 `GET /finder-preview/api/feed/get_feed_info` 获取元信息。但该接口带签名校验——页面加载时的首次调用由 JS SDK 签名，脱离页面上下文重放（curl 或页面内重新 fetch）均返回 `{"errCode":-1,"errMsg":"permission verification failed"}`。
4. **唯一可拿的媒体**：封面缩略图（`finder.video.qq.com/.../stodownload?encfilekey=...&token=...`），地址本身也带时效签名，会过期。

## 结论

- **视频号链接的自动化服务端提取：不可行。** 官方网页预览页故意不放视频（引导回微信客户端），数据接口有签名鉴权，视频字节只能在微信客户端登录态内获取且 2023 年后带密钥加密。任何"粘贴视频号链接自动入库"的功能都会随微信升级随时失效。
- **视频号历史内容的可行路线（人工）**：两种人工抢救通道，版权均为部门自有，风险可控：
  1. **第三方下载助手公众号**：在微信里把视频号视频转发给这类服务号，它会回一条视频下载链接——原理是对方运营者在服务器上跑了登录态的微信协议机器人，替你在客户端内完成下载再回传。链接有时效，收到后立即下载，再上传到本系统永久保存。注意：这类服务随时可能被微信封禁关停，只能当临时工具，不能作为系统依赖。
  2. **PC 微信 + 下载工具**：自己电脑操作（如 wechatVideoDownload 类开源工具，注入 PC 微信拿地址和解密密钥）→ 得到 MP4 → 上传到本系统。
- **公众号文章链接（mp.weixin.qq.com）的视频导入：可行，纳入功能 F1.5。** 文章是公开网页，嵌入视频地址可解析（vid → 播放地址），服务端可自动下载。按 best-effort 维护，微信改结构时需跟进修复，失败时转人工兜底。

## 为什么不能自建"下载助手"（2026-09-17 补充决策）

用户提出能否把"视频号下载助手"做成系统子功能。结论：**服务器端微信协议机器人不做**，三个硬理由：

1. **封号风险**：协议机器人（模拟 iPad/PC 微信登录的非官方客户端）违反微信用户协议，是腾讯重点打击对象，封号是常态。机器人必须挂一个真实微信号，无论挂谁的号，被封代价都承受不起。
2. **合规风险**：你们是广播电视台（体制内单位），协议破解类软件在国内已有反不正当竞争乃至刑事判例，装进官方系统性质完全不同。
3. **工程脆弱**：开源协议实现随微信升级频繁失效，稳定的都是灰色付费服务，生产系统不能建在这种地基上。

第三方下载助手公众号能存在，是因为运营者用一次性账号吸收封号风险、以此收费——那是别人的生意模式，不是我们能复制的能力。

替代方案：系统内做"视频抢救工作台"（SOP 指引 + 上传 + 自动流水线），把人工抢救变成标准化操作；远期（M4）可评估做一个**本机辅助小工具**（在操作者自己的电脑上、借用本人微信登录态、偶发使用的抓取+自动上传脚本），风险与服务器机器人完全不同量级，但同样按 best-effort 对待。

## 对系统设计的含义

- F1.5 链接导入工具**只接受公众号文章链接**，UI 文案明确提示"不支持视频号链接"
- 日常主流程仍是"剪辑导出原始成片 → 直接上传本系统"，画质最好、地址永久有效
- 系统同时承担部门成片资产库职责，减少对视频号的依赖
