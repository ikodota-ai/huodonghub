# 控制台群体选择与提交权限统一设计

## 背景

当前“开始本轮”会同时允许专家、大众和开放观众组提交，`screenGroupId` 只控制大屏展示。提前获得观众二维码的人可以在大屏仍显示专家时投票，控制台选择与实际权限不一致。

## 已确认规则

控制台选择的群体同时是大屏展示群体和本轮唯一可提交群体：

- 选择某个专家组：只有该组评审可评分，大众和观众不能提交。
- 选择某个大众组：只有该组评审可评分或投票，专家和开放观众组不能提交。
- 选择某个开放观众组：只有观众可投票，专家和大众不能提交。
- 选择“总分”：仅展示结果，暂停所有群体提交。
- 活动已结束/归档或轮次未处于 `active` 时，无论选择什么都禁止提交，原有优先级不变。

以上规则必须同时作用于页面和直接 API 请求，不能只做前端隐藏。

## 技术方案

复用现有 `vote_rounds.screen_group_id`，不增加数据库字段或迁移。新增无副作用的群体提交判定：活动可提交、轮次 `active`、`screenGroupId` 非空且与当前 `groupId` 完全一致时才允许提交。

### 评委端

- `GET /api/judge/{token}` 返回当前群体是否开放，页面在未开放时显示“当前未开放本群体评分/投票”，不渲染提交表单。
- `POST /api/judge/{token}` 复用已查询的 `round.screenGroupId` 和 `voter.groupId` 校验；不匹配返回 403，不开启写入事务。
- 历史成绩回显、活动生命周期、批次和绑定规则保持不变；此前讨论的绑定漏洞修复不在本次范围内。

### 开放观众端

- `GET /api/vote/{code}` 只在当前 `screenGroupId` 指向开放观众组时返回该组可投状态；选择其他群体或总分时显示“投票未开放”。
- `POST /api/vote/{code}` 在原 SQL 的群体 JOIN 中要求 `g.id = r.screen_group_id`，继续一次取得上下文，不增加高频数据库往返。选择专家、大众、总分或组不匹配时返回 403。
- 限流、配额、批次、指纹/openid、计数器和 SSE 语义不变。

### 控制台与大屏

- 原“大屏显示内容”改为明确的双重含义，例如“当前开放群体（同步大屏显示）”。
- “总分”选项标注“关闭所有提交”，并提示切换会立即影响对应页面和 API。
- 复用现有 console `screen` action 和 SSE 发布，不增加新接口；大屏本地快捷键不获得管理权限。

## 兼容与测试数据

- 新轮次 `screenGroupId` 为空时默认相当于“总分”，所有提交关闭，避免提前投票。
- 既有活动部署后，选择总分的轮次会关闭所有提交；选择具体群体的轮次只开放该群体，需要在上线说明中明确。
- 生命周期及评分浏览器场景在提交前切换到对应群体。
- 压测 fixture 创建观众组后将 `screenGroupId` 设置为该组，否则不得开始压测。

## 验证

- Node：专家、大众、观众分别只允许选中组；总分全部拒绝；轮次暂停/结束和活动结束优先；直接 POST 无绕过且不写流水。
- 浏览器：控制台依次切换专家、大众、观众、总分，各类页面和直接 API 同步变化。
- 回归：相关 Node 全量、TypeScript、Prisma、ESLint、生产构建和生命周期场景。
- 部署：安装前核对新 BUILD_ID，部署后核对线上 chunk 与 OSS；使用专用活动验证群体切换，并按需复测 2000 人/10 秒观众场景。

## 非目标

- 不实现独立观众开关、预约时间编辑或每组独立倒计时。
- 不处理评审二维码绑定漏洞，不改变总分计算和大屏视觉。
