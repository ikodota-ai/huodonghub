# 投票完整链路压力测试设计（2026-11-06）

## 目标

验证现场 **2000 名观众在 10 秒内扫码打开页面，并每人完成 3 票** 时，投票页面、写入接口、MySQL、大屏 SSE 与实时结果链路是否稳定。

目标峰值：

- 页面与选手加载：2000 人 / 10 秒，约 200 人/秒。
- 投票写入：6000 次 / 10 秒，约 600 次/秒。
- 大屏至少 1 条 SSE 长连接，后台控制台至少 1 个在线页面。

压力测试先测现状，不预设需要优化；只有实测暴露出瓶颈后，才根据证据做最小改动并复测。

## 方案选择

采用完整链路压测（方案 B）：模拟扫码打开投票页、加载首屏静态资源与选手、提交 3 个不同选手的投票，同时保持大屏 SSE 和后台控制台在线。

不采用只压写入接口的方案 A 作为最终验收，因为它无法发现公网带宽、Nginx、静态资源或大屏刷新放大问题。若单台压测机先达到 CPU/带宽瓶颈，再升级为多机压测（方案 C）。

## 数据安全与前置条件

- 使用独立的专用测试投票和轮次，禁止选择正式活动。
- 测试轮次配置：开放观众投票、设备指纹模式、每人 3 票、不允许重复投同一选手、轮次进行中。
- 每轮压测生成唯一 `runId`，并为每位模拟观众生成唯一指纹；只投票给接口返回的有效选手。
- 不使用匿名压测后门，不修改生产投票接口的鉴权、重复投票或限流规则。
- 压测机的所有请求可能共享一个出口 IP。测试前记录 `vote.ipLimit` 原值，仅在专用测试环境临时调高阈值；请求仍执行原有 IP 统计查询，结束后恢复原值。
- 记录测试投票 ID、轮次 ID、群体 ID 和 `runId`。只按这些标识核对与清理测试数据，禁止全表清空。
- 压测前备份数据库；清理后核对配置、选手、正式票数和正式评分未变化。

## 压测链路

每位模拟观众执行：

1. GET `/vote/{code}`，取得投票 HTML。
2. 请求 HTML 中首屏所需的 JS/CSS 静态资源；选手图片单独统计下载量与失败率。
3. GET `/api/vote/{code}?fp={唯一指纹}`，校验活动、群体、选手和剩余票数。
4. 从有效选手中选取 3 个不同选手，顺序 POST `/api/vote/{code}`。
5. 校验每次响应的业务状态和剩余票数，确保恰好产生 3 条有效投票。

同时执行：

- 保持大屏 `/api/screen/{roundId}/stream` 长连接，记录断线与重连。
- 大屏页面正常监听更新并请求 state，观察投票高峰期间是否出现请求堆积、刷新延迟或页面跳变。
- 后台控制台保持在线，观察参与率刷新是否放大数据库压力。

## 场景

| 场景 | 规模 | 目的 |
|---|---|---|
| 冒烟 | 50 人 / 10 秒，共 150 票 | 验证脚本、业务配置、数据核对与清理流程 |
| 基准 | 200 人 / 10 秒，共 600 票 | 获取低压力基线，检查监控与报告 |
| 目标 | 2000 人 / 10 秒，共 6000 票 | 验证本次活动预计峰值 |
| 余量 | 3000 人 / 10 秒，共 9000 票 | 目标通过后再运行，验证 1.5 倍余量 |

每个场景独立生成 `runId`。场景失败时先保留报告和服务器监控，不直接扩大到下一场景；修复后以相同参数复测。

## 指标与验收

### 正确性

- 非预期 5xx、业务校验错误和重复计票为 0；网络错误单独报告，不用自动重试掩盖。
- 目标场景恰好 2000 名唯一测试观众、6000 条投票明细，每人 3 票且选手不重复。
- `vote_entries` 明细、`group_stats` 计数、结果 API 与大屏数值一致。
- 大屏 SSE 无异常永久断开；高峰结束后 2 秒内能展示最终结果。

### 性能

- 目标场景下页面/选手 GET 与投票 POST 的 P95 不超过 1 秒，P99 不超过 2 秒。
- 报告吞吐量、每秒请求数、响应时间分布、失败率、静态资源字节数和公网带宽占用。
- 记录 Node/PM2 CPU、RSS、重启次数、系统内存与 Swap、MySQL 活跃/峰值连接数、慢查询和锁等待。
- 不发生 OOM、PM2 异常重启、MySQL 连接耗尽或无法继续访问后台。

若公网链路先达到带宽上限，应明确标记为“网络瓶颈”，不能用服务器回环结果冒充公网验收通过。

## 执行位置与产物

- 公网验收从阿里云服务器之外的压测机发起，覆盖 DNS、公网、Nginx、Node 与 MySQL。
- 服务器回环压测只用于拆分应用/数据库瓶颈，不作为公网验收结论。
- 压测脚本不写入真实域名、数据库密码或密钥，统一通过环境变量传入。
- 产物保存到 `output/load-test/{runId}/`：k6 摘要 JSON、文本报告、服务器资源监控、票数核对 SQL 结果和清理记录；正式报告写入 `doc/load-test.md`。

## 边界

- 本轮只压测现有系统并定位瓶颈，不同时开发“细分评分”，避免功能变化干扰性能结论。
- 不压测视频上传、转码、视频播放和微信 OAuth。
- 不通过关闭重复投票约束、删除索引或跳过业务校验换取虚假吞吐量。
